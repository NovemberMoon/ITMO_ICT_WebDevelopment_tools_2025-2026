## 1. Введение

**Цель работы:** понять отличия между потоками и процессами и понять, что такое асинхронность в Python.

**Цель первой задачи:** на практике изучить разницу между многопоточным, многопроцессным и асинхронным подходами при выполнении задачи с высокой вычислительной нагрузкой (CPU-bound).

В рамках первой задачи требовалось разработать программы, вычисляющие сумму чисел от 1 до N. Для ускорения выполнения общая зоснове–адача должна быть разделена на несколько параллельных подзадач с использованием модулей `threading`, `multiprocessing` и ключевых слов `async/await` модуля `asyncio`. Итоговым этапом является профилирование разработанных алгоритмов и анализ их эффективности.

_Примечание к масштабу вычислений:_ В исходном задании указан диапазон до 10^13. Поскольку алгоритмическая сложность вычисления суммы с помощью цикла составляет O(N), выполнение такой задачи на языке Python занимает несколько суток машинного времени. Для получения репрезентативной статистики и возможности проведения многократных тестов, профилирование в данной работе производилось на значениях N = 10^8 и N = 10^9.

## 2. Архитектура и программная реализация

Для реализации задачи и проведения прозрачных экспериментов кодовая база была разделена на изолированные модули в директории `src/task1/`. Разработана следующая файловая структура:

- `task1_runner.py` – главный скрипт-оркестратор.

- `task1_sync.py` – эталонный синхронный код (baseline) для оценки базовой скорости выполнения в одном потоке.

- `task1_threading.py` – реализация на основе системных потоков.

- `task1_multiprocessing.py` – реализация на основе изолированных процессов ОС.

- `task1_async.py` – реализация на основе корутин и цикла событий.

- `test_task1.py` – модуль unit-тестов, проверяющий математическую корректность подходов.

Во всех подходах используется идентичная целевая функция `calculate_sum`, имитирующая интенсивную нагрузку на процессор путем сложения чисел:

```python
def calculate_sum(start: int, end: int) -> int:
    """Имитация тяжелой нагрузки на процессор (вычисление суммы)"""
    total = 0
    for i in range(start, end + 1):
        total += i
    return total
```

### 2.1. Многопоточный подход (модуль threading)

В многопоточной реализации (`task1_threading.py`) общая задача разбивается на равные части, каждая из которых отдается отдельному системному потоку `threading.Thread`. Главной особенностью данного подхода является функционирование потоков внутри единого адресного пространства оперативной памяти. В коде главный поток заранее создает массив `results`, а каждый дочерний поток записывает вычисленную сумму строго по выделенному ему индексу.

```python
def calculate_sum(start: int, end: int, results_list: list, index: int):
    total = 0
    for i in range(start, end + 1):
        total += i
    results_list[index] = total

# Фрагмент запуска потоков:
for i in range(num_tasks):
    start = i * step + 1
    end = (i + 1) * step if i != num_tasks - 1 else target_number
    thread = threading.Thread(target=calculate_sum_thread, args=(start, end, results, i))
    threads.append(thread)
    thread.start()
```

### 2.2. Многопроцессный подход (модуль multiprocessing)

Программа `task1_multiprocessing.py` распределяет вычисления между пулом независимых процессов ОС, используя модуль `multiprocessing`. Особенностью данной архитектуры является обход ограничений GIL. Каждый процесс инициализирует собственный интерпретатор Python и обладает выделенной, изолированной областью памяти. Это позволяет задействовать физические ядра процессора. Поскольку метод `pool.map` передает в функцию-обработчик только один аргумент, границы вычислений предварительно упаковываются в кортежи.

```python
def calculate_sum(args: tuple) -> int:
    start, end = args
    total = 0
    for i in range(start, end + 1):
        total += i
    return total

# Фрагмент запуска процессов
for i in range(num_tasks):
        start = i * step + 1
        end = (i + 1) * step if i != num_tasks - 1 else target_number
        tasks_args.append((start, end))

    with multiprocessing.Pool(processes=num_tasks) as pool:
        results = pool.map(calculate_sum, tasks_args)
```

### 2.3. Асинхронный подход (модуль asyncio)

Асинхронная программа `task1_async.py` базируется на кооперативной многозадачности внутри одного системного потока. Вычислительная логика обернута в корутину, а сгенерированные подзадачи конкурентно передаются в цикл событий (Event Loop). Отличительной чертой данного подхода является то, что при отсутствии операций ввода-вывода (I/O-ожиданий) корутины полностью блокируют цикл событий, заставляя код выполняться строго последовательно, добавляя при этом накладные расходы на работу самого цикла.

```python
async def calculate_sum(start: int, end: int) -> int:
    total = 0
    for i in range(start, end + 1):
        total += i
    return total

# Фрагмент запуска корутин
tasks = []
for i in range(num_tasks):
    start = i * step + 1
    end = (i + 1) * step if i != num_tasks - 1 else target_number
    tasks.append(calculate_sum_async(start, end))

results = await asyncio.gather(*tasks)
```

## 4. Анализ результатов и сравнение подходов

Опираясь на полученные метрики, можно сделать следующие выводы о механике выполнения CPU-bound задач в Python:

1. **Деградация Threading и специфика Asyncio:**

    Как видно из Таблицы 3.1, многопоточный код (`Threading`) стабильно выполняется **медленнее** обычного синхронного цикла (~10.5 сек против ~9 сек). В то же время асинхронный подход (`Asyncio`) в большинстве тестов **обгоняет** базовый синхронный код (показывая ~7.82 сек). Однако ни один из этих подходов не дает параллельного ускорения на нескольких ядрах:
    
    - **Проблема Threading (Конкуренция за GIL):**

        Глобальная блокировка интерпретатора (GIL) не позволяет потокам выполняться параллельно. Потоки работают по очереди, но при этом они вынуждены постоянно бороться за захват блокировки (lock contention). Операционная система тратит процессорное время на прерывания и переключение контекста (сохранение регистров одного потока и загрузку другого). Вместо полезных вычислений процессор загружен обслуживанием самих потоков, что снижает производительность ниже базового уровня.

    - **Почему Asyncio обгоняет Sync, но не дает параллелизма:**

        Асинхронность в Python является кооперативной: корутина отдает управление только при явном вызове `await`. Поскольку внутри нашего математического цикла нет пауз или ввода-вывода (нет операторов `await`), первая запущенная корутина монопольно захватывает ядро и не прерывается до конца вычислений. Команда `await asyncio.gather()` лишь инициирует выполнение задач, но они обрабатываются циклом событий **строго последовательно**, одна за другой.
        Тот факт, что Asyncio выполняется немного быстрее базового синхронного кода, связан исключительно с внутренними оптимизациями интерпретатора CPython: корутины чуть эффективнее работают с локальными переменными, а Event Loop запускает их без системных прерываний. Однако при увеличении количества задач (Таблица 3.2) время не ускоряется (держится около 60 секунд), так как физически код заперт в пределах одного ядра.

2. **Масштабируемость Multiprocessing и аппаратные лимиты:**

    Многопроцессность оказалась единственным инструментом, показавшим реальное ускорение. При создании новых процессов ОС запускает независимые копии интерпретатора Python со своими собственными GIL, что позволяет распределить нагрузку по разным физическим вычислительным ядрам.
    Время выполнения линейно сократилось с 36.47 секунд (на 2 процессах) до 16.39 секунд (на 8 процессах). При этом стагнация результата на 16 процессах (16.29 сек) имеет логичное физическое объяснение: поскольку используемый процессор имеет всего **8 логических ядер**, после отметки в 8 воркеров он упирается в свой аппаратный предел. Процессам приходится делить между собой процессорное время, из-за чего дальнейшего прироста скорости не происходит.

## 5. Заключение

Опытным путем доказано, что для программ, решающих тяжелые математические задачи (и любые другие CPU-bound операции), использование модулей `threading` или `asyncio` нецелесообразно из-за накладных расходов на переключение контекста, конкуренции за блокировку и специфики кооперативной многозадачности. Ни один из этих подходов не способен распараллелить вычисления. Для получения реального масштабирования необходимо применять модуль `multiprocessing`, эффективность которого напрямую ограничена количеством доступных логических ядер процессора.
